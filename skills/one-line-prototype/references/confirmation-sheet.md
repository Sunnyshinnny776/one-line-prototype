# 确认单

本文件在流程第 8 步交付时使用，第 9 步修改后更新确认单时也用。它规定确认单写什么、怎么排，以及交付回复的格式。

## 确认单是什么

确认单列出 PRD 里哪些内容是 skill 自己补的、哪些问题没确认、哪些和用户已有的文档冲突。用户拿到 PRD 后，只看确认单和原型，就能判断哪些地方要改。

- 确认单是单独的 HTML 文件，放在输出目录下，文件名是 `<需求名>-确认单-交付前必看.html`。对话里的表格在有些终端里显示不成表格；一条有六项内容，写成表格又宽又挤。HTML 版左侧是目录，右侧一条一张卡片，双击用浏览器打开，断网也能看。
- 不另出 Markdown 版，两份并存容易内容不一致。
- 文件名里带"交付前必看"，是提醒用户把 PRD 和原型交出去之前，先看完这份文件。确认单里的条目没核对就交出去，skill 补的内容会被当成用户定下的要求。
- 确认单只给用户本人看。它的内容不得出现在 PRD 和原型里。PRD 和原型要交给评审人、研发和外包方，这些人看到"这条是我补的"，会以为整份文档都没有定下来。
- 同名文件已存在时不覆盖，先告诉用户，由用户决定覆盖还是另存。

## 怎么写这个文件

1. 完整读 `assets/confirmation-base.html`，复制全部内容。
2. 只改"确认单内容"脚本块里的 `SHEET`，把示例内容整段换掉。样式和脚本不改，每次生成的样子一致。确认单始终用这个样式，用户提供了界面参考也不换。
3. 页面上的标题、开头那句"只给你本人看……"、条数统计、目录和卡片都由脚本根据 `SHEET` 生成，不手写。

`SHEET` 的写法：

```js
const SHEET = {
  title: '{需求名称}',
  items: [
    { no: 1, type: '{我补的 / 未确认 / 和历史文档冲突}', where: '{位置}', short: '{目录里的简称，可省略}', prd: '{PRD 里写的}', basis: '{依据}', fix: '{不对的话要改哪里}' }
  ],
  advice: [
    { no: {接着 items 的最大编号}, element: '{页面元素}', now: '{现状}', suggest: '{建议做法}', basis: '{依据}' }
  ],
  notes: [
    '{一条一句}'
  ]
};
```

- `items` 对应"需要你确认的内容"，`advice` 对应"交互建议"，`notes` 对应"说明"。没有内容的部分写空数组，页面上整段不出现。
- `short` 省略时，目录显示 `where` 去掉开头章节号的部分，如"3.1.3 R3 单次退货金额上限"显示为"R3 单次退货金额上限"。`where` 太长时写一个短的 `short`。
- 字符串里的单引号写成 `\'`，或者整句改用双引号包起来。

## 需要你确认的内容

列出 PRD 里所有用户还没确认过的内容，一条一张卡片。卡片上最醒目的是"PRD 里写的"，用户先看到内容本身，再看位置和依据。类型有三种：

| 类型 | 什么时候用 | `basis` 写什么 | `fix` 写什么 |
| --- | --- | --- | --- |
| 我补的 | skill 自行补全的规则、数值、范围 | 补的理由。边界值写出推导：场景平时的量级、边界定在哪里、为什么平时碰不到，见 prd-template.md 的"补的规则要贴合场景" | 不成立时要跟着改的位置 |
| 未确认 | 没问到的问题，或用户没回答的问题，按推荐值写进了 PRD | 只有两种写法："没问到，按推荐值写的"或"你没回答，按推荐值写的"。没有向用户提问过的，不得写"已提出""已确认" | 这个取值涉及的位置 |
| 和历史文档冲突 | 本次内容和用户已有文档不一致 | "历史文档写的是……" | 建议怎么处理 |

- `where` 写到能直接找到的程度：章节号加规则编号和规则名称，或页面名加字段名。用户要能只回一句话就说清改哪里。
- 按影响范围从大到小排。改流程或状态的排在前面，只改一个文案的排在后面。
- "我补的"列写错了会影响实现的条目。不为了压缩篇幅省略条目，漏掉一条，用户就不知道那里是 skill 猜的。
- "我补的"的依据不能只写"常见做法""常用默认值""常用选项"，要写出它和这个场景的关系。业务数值，如税率、保留期、整改期限，写为什么这个场景取这个值；拿不准时写"这个值我不确定，需要你给"。纯界面默认值，如每页条数、默认排序，写"界面默认值，不影响业务规则"即可。
- 条数不设上限。不要为了让确认单短一些而少补 PRD 和原型该有的内容：该补的照补，补了的照记。
- 原型里的示意内容不进确认单，见 prototype-rules.md 的"规则、交互设计和示意内容"。

## 交互建议

只在用户提供了界面参考时出现。范围、数量和采纳方式见 prototype-rules.md。编号接着"需要你确认的内容"往下排，用户说"采纳第 N 条"时不会撞号。

## 说明

一条一句，写用户需要知道、但不涉及 PRD 内容的事：

- 原型里已有页面的内容和示例数据是示意，不代表现有系统的实际字段。
- 用了默认模板。
- 用了默认样式。原型右上角的"规则标注"开关可以关掉规则灯泡，用于演示。
- 移动端没有套用专门规范。
- 流程偏复杂，拆成了多张流程图。
- 流程图没有经过目视检查。只在确实没有转成图片查看时写这一条，看过的不写。
- 简化流程没有做的事。只在判为复杂、用户选择不安装完整流程时写；判为简化的需求不写这一条。见 intake-grading.md。

## 写法要求

- 自查和测试的过程、结果不写进确认单，例如"流程图看过，没有重叠""原型点过一遍，都通了"。确认单只列要用户判断的事，检查过没有问题的事不需要用户判断。
- 确认单的编号只用在确认单和对话里，不得出现在 PRD 里，包括修改记录。
- 确认单也遵守 writing-rules.md 的规则。

## 完整性要求

PRD 里每一个具体数值、每一条规则，来源必须是下面三种之一：

1. 用户的输入或历史文档。
2. 用户对提问的回答。
3. skill 自己补的，并且列在确认单里。

不允许有第四种情况，即 skill 补了但没有列进确认单。交付前把 PRD 里的数值和规则逐个对一遍来源，找不到来源的补进确认单。确认单漏掉的内容，用户以为是自己说过的，会直接交给研发。

## 交付回复的格式

交付时的回复只写下面三样，按顺序写。不贴确认单的内容，不复述用户的回答，不写自查和测试的过程：

1. PRD、流程图、原型和确认单的文件位置，标明确认单只给用户看。
2. 一句话说明确认单有几条，影响最大的是哪一条。
3. 一句话说明下一步可以怎么改。

## 修改后更新确认单

用户按确认单改了内容后，同步更新确认单文件里的 `SHEET`：

- 用户确认过或改过的条目，整条删掉。
- 修改带出的新的补充内容，加在 `items` 里，`no` 接着全文最大编号往下排。
- 已有条目的 `no` 不改。用户可能还在用旧编号说话。
- 回复里写明 PRD 和原型改了哪些位置，确认单删了哪几条、加了哪几条。

## 示例

需求是"给门店加一个退货申请功能，店员提交，区域经理审核"。数值都是示例值。

确认单文件 `退货申请/退货申请-确认单-交付前必看.html` 里的 `SHEET`：

```js
const SHEET = {
  title: '退货申请',
  items: [
    { no: 1, type: '我补的', where: '3.1.3 R3 单次退货金额上限', prd: '单次退货金额超过 5000 元时，区域经理和财务各审核一次', basis: '你没有提到金额限制。门店单件商品多在几百元，一次退货通常一两件；超过 5000 元的退货很少见，金额这么大时多一道财务审核，平时的退货不受影响', fix: '流程图、审核页面和状态流转都要去掉财务审核这一步' },
    { no: 2, type: '未确认', where: '3.1.3 R5 撤回条件', prd: '待审核状态下店员可以撤回申请', basis: '没问到，按推荐值写的', fix: 'R5 和申请详情页的"撤回"按钮' },
    { no: 3, type: '我补的', where: '3.1.2 申请表单，退货原因', short: '申请表单的退货原因', prd: '选项为质量问题、尺码不合适、顾客改变主意、其他', basis: '门店退货的原因主要是商品质量、尺码和顾客改主意三类，加"其他"兜底；你没有给选项', fix: '只影响这个选项组' },
    { no: 4, type: '我补的', where: '3.1.2 申请列表，每页条数', short: '申请列表每页条数', prd: '10 条', basis: '界面默认值，不影响业务规则', fix: '只影响列表分页' }
  ],
  advice: [],
  notes: [
    '你没有提供历史文档，PRD 用的是默认结构。',
    '你没有提供界面参考，原型用的是默认的后台样式。原型右上角的"规则标注"开关可以关掉规则灯泡，用于演示。',
    '原型里已有页面的内容和示例数据是示意，不代表现有系统的实际字段。'
  ]
};
```

交付回复：

```
已生成四样文件，都在 退货申请/ 目录下：

- 退货申请-PRD.md
- assets/退货申请-提交与审核-流程图.svg
- 退货申请-原型.html（直接用浏览器打开）
- 退货申请-确认单-交付前必看.html（只给你看，不要随 PRD 发出）

确认单里有 4 条要你确认，影响最大的是第 1 条：我补了一条"超过 5000 元要财务再审一次"的规则。

要改哪里，直接说一句，我会同时改 PRD、原型和确认单。
```

上面的例子没有交互建议，也没有"和历史文档冲突"的条目，所以页面上不出现交互建议这一段。
