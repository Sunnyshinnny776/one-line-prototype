# 精简 PRD 模板

本文件在流程第 5 步使用。它规定 PRD 的结构从哪里来、默认模板有哪些章节、每章写什么。句子怎么写见 writing-rules.md，流程图怎么画见 flow-diagram.md。

## 结构从哪里来

按下面的顺序确定，用到第一个适用的为止。

1. 用户提供了历史文档：按下一节"用户提供了历史文档时"做。
2. 用户没有提供：用本文件的默认模板。交付时在确认单的"说明"部分里写明用的是默认模板。

## 用户提供了历史文档时

历史文档指用户以前写的 PRD、需求说明或方案文档。PRD 要读起来像用户团队自己写的，评审人不用适应新格式，所以结构和用语跟着历史文档走。

1. 历史文档是只读的样本。任何情况下都不修改、不覆盖用户给的历史文档文件，产出一律写成新文件。用户给的界面参考等其他文件同样不动。这些是用户团队的正式文档，被改了用户不一定发现。
2. 读完整份文档，记下四样东西：章节结构和顺序、编号方式、术语表（每个对象叫什么）、表格的列结构。
3. 默认只写本次需求。新文档沿用这四样，但只包含本次需求的内容：不照搬已有功能的章节，不接着历史文档的版本号往下排，不沿用它的编写人。规则编号用历史文档的写法，接着它的最大编号往下排，全文一致，这样不会和已有规则撞号。引用历史文档里的规则或章节时写明出处，如"V2.3 的 GZ-01 台账范围"，读者才知道去哪份文档找。
4. 历史文档就是本次需求的上一个版本时，即同一个模块、本次在它上面迭代或补充，按 questions.md 问用户要单独写一份还是出完整的新版本。没问到或没回答时按单独写一份，并记入确认单。
5. 用户选出完整的新版本时：新文件包含原有章节和本次的增补，版本号接着原文档往下排，修订记录加一行。原有章节只改和本次需求有关的地方，改了哪些原有章节逐条记入确认单。新版本另存为新文件，原文件不动。
6. 历史文档是方案类文档而不是 PRD 时，同样按它的结构写。
7. 只写和本次需求规模相称的章节。历史文档的章节多，不为了章节数一致而硬填。
8. 本次内容和历史文档冲突时的处理见 writing-rules.md。

## 默认模板的章节

| 类别 | 章节 | 出现条件 |
| --- | --- | --- |
| 固定 | 文档信息与修改记录 | 始终 |
| 固定 | 1. 需求概述 | 始终 |
| 固定 | 2. 范围 | 始终 |
| 固定 | 3. 功能需求 | 始终 |
| 固定 | 4. 验收要点 | 始终 |
| 按需 | 状态流转 | 有带状态的业务对象 |
| 按需 | 异常处理 | 有本需求里会发生的异常 |
| 按需 | 角色和权限 | 有 2 个及以上角色 |
| 按需 | 术语 | 出现读者可能不认识的名词 |
| 按需 | 风险 | 用户提到了风险，或需求依赖尚未具备的条件 |
| 按需 | 数据埋点 | 用户提到要统计或跟踪 |

- 按需章节放在"3. 功能需求"之后、"4. 验收要点"之前，从 4 开始编号，验收要点的章节号依次顺延。
- 出现条件不成立的按需章节整章不出现，不留占位文字。空章节让读者以为漏写了。
- 商业分析、方案概述与架构图、参考文献、运营计划不进 PRD。它们回答的是立项问题，这个规模的需求用不上。
- 待决事项和待完善清单不进 PRD，写进确认单。它们是给用户本人看的，评审人和研发不需要。

## 各章的内容要求

### 文档信息与修改记录

- 文档信息只写有值的项：标题、版本、日期。编写人、需求方、审核人只在用户提供了时才写，没有就整行不写。
- 修改记录的列为：日期、修改内容、版本号。初稿写一行。

### 1. 需求概述

- 背景：为什么要做，一到三句。只写用户说过的，或能从输入直接得出的。
- 目标：做完后要达到什么结果。
- 用户与场景：用表格写，列为用户、场景、用它做什么。这里的"用户"指使用这个功能的人，如店员、区域经理，不是提需求的用户。

### 2. 范围

- 本次做什么，逐项列出。
- 本次不做什么，逐项列出。
- 本次改的是已有页面时，只加本次需求的内容，不改它原有的展示、筛选和数据范围。确实要改时，写成一条规则，并记入确认单。

### 3. 功能需求

每个功能写成一个小节，如 3.1、3.2，每个小节按"流程、页面交互、业务规则"三段写。

流程：

- 每个功能一张流程图，画法见 flow-diagram.md，在本段开头用图片引用。
- 图后写文字说明。主流程用编号步骤写，3 到 7 步，每步写清谁、做什么、系统给出什么结果。
- 分支和回退路径单独列在主流程之后。
- 文字说明和流程图的步骤一一对应，步骤名称用同一个说法。
- 不画架构图。

页面交互：每个页面和每个弹层各写一组规则块。一个功能有多个页面时，每个页面各写一组。内容照第 4 步列的页面清单写（见 prototype-rules.md）：主操作放在哪、弹层里展示哪些信息、哪些规则以界面文字的形式出现，都写进对应的规则块。PRD 只写"点按钮弹出确认框"，原型就只能做出一个一句话的确认框。下表是八个规则块，前四个每个页面都要写，后四个按出现条件写。

| 规则块 | 出现条件 | 表格的列 |
| --- | --- | --- |
| 页面结构 | 始终 | 区域、内容、交互 |
| 字段规则 | 始终 | 列表字段：字段、显示格式、交互与校验、权限与状态。表单字段：分区、字段、读写、控件与格式、必填条件、校验与联动 |
| 按钮规则 | 始终 | 按钮、展示条件、点击反馈、阻断条件、禁用态表现 |
| 页面状态与文案 | 始终 | 状态、触发条件、文案与交互 |
| 查询条件 | 页面有筛选或搜索 | 控件、字段类型、输入限制、触发规则、错误与空态 |
| 弹窗与抽屉规范 | 页面有弹层 | 容器类型、尺寸、按钮组、未保存时关闭的处理 |
| 控件交互态 | 用户要求，或控件有特殊状态 | 元素、默认态、悬停态、聚焦态、错误态、禁用态 |
| 敏感字段 | 有需要脱敏的字段 | 字段、脱敏格式、查看方式、导出口径 |

各列写什么：

| 规则块 | 列 | 写什么 |
| --- | --- | --- |
| 页面结构 | 区域 | 顶栏、提示条、标签页、查询区、列表、分页等 |
| 页面结构 | 内容 | 区域里的元素清单，含按钮名 |
| 页面结构 | 交互 | 触发方式，区域之间的联动，切换时保留什么、清空什么 |
| 字段规则，列表 | 显示格式 | 文本长度上限、日期格式、金额精度、状态徽标的颜色、空值显示什么 |
| 字段规则，列表 | 交互与校验 | 超长时省略并在悬停时显示完整内容、能否复制、点击后去哪里、能否排序 |
| 字段规则，列表 | 权限与状态 | 数据从哪里来、什么情况下能编辑、是否脱敏 |
| 字段规则，表单 | 读写 | 只读、可编辑、条件可编辑三选一 |
| 字段规则，表单 | 控件与格式 | 控件类型、格式、精度、默认值 |
| 字段规则，表单 | 必填条件 | 必填、选填，或写清触发条件的条件必填 |
| 字段规则，表单 | 校验与联动 | 取值范围、上限、和其他字段的联动、校验不通过时的错误文案 |
| 按钮规则 | 展示条件 | 什么角色、什么数据状态下出现 |
| 按钮规则 | 点击反馈 | 加载状态、提示、跳转、二次确认 |
| 按钮规则 | 阻断条件 | 哪些校验不通过时不能执行 |
| 按钮规则 | 禁用态表现 | 置灰，悬停时显示禁用原因 |
| 页面状态与文案 | 状态 | 从首次加载、空数据、搜索无结果、无权限、部分权限、加载或保存失败里选本页面会出现的 |
| 查询条件 | 输入限制 | 长度上限、去掉首尾空格、默认选中项 |
| 查询条件 | 触发规则 | 改条件后什么时候生效，点"重置"后条件和页码怎么复位 |
| 查询条件 | 错误与空态 | 没有结果时的文案，查询失败时的提示 |
| 弹窗与抽屉规范 | 容器类型 | 弹窗、抽屉或新页面 |
| 弹窗与抽屉规范 | 尺寸 | 写"默认宽度"或"加宽"，不写像素数。确实要定一个具体宽度时，这个数值记入确认单 |
| 弹窗与抽屉规范 | 按钮组 | 只读模式和编辑模式各有哪些按钮 |
| 弹窗与抽屉规范 | 未保存时关闭的处理 | 二次确认的文案，保存中的加载状态，防止重复提交 |
| 敏感字段 | 脱敏格式 | 写出具体的掩码样式 |
| 敏感字段 | 查看方式 | 怎么临时查看完整内容、怎么再隐藏 |
| 敏感字段 | 导出口径 | 导出时是否同样脱敏 |

字段规则写到什么粒度，见 writing-rules.md。

业务规则：

| 列 | 要求 |
| --- | --- |
| 编号 | `R1`、`R2` 依次编号，全文连续，不按功能重新起号 |
| 规则类型 | 事实、约束、触发条件、推论、计算，五选一 |
| 规则描述 | 开头写规则名称，后面写完整内容。完整内容写清谁、在什么条件下、做什么、结果是什么 |

规则名称在三处共用：验收要点的"对应规则"列、正文引用规则时、原型里规则灯泡展开的内容。名称一处定下，三处一致，读者才能对上号。

补的规则要贴合场景。用户没说、由你补的规则，按下面五条定：

1. 边界和异常要写。数量上限、时间跨度、超时、文件过期、重复提交、失败后怎么办，属于产品规则，PRD 里定下来，不留给研发。要补，但要补对。
2. 取值从场景推。先按用户说的场景估出平时的量级，例如"区域经理每周审核一次，一个区域一周有几十条退货申请"，再把边界值定在平时用不到、离谱时才触发的位置。不套一个常见的数字。怎么推的写进确认单的"依据"。
3. 边界规则不妨碍主流程。按用户说的场景、用默认操作走一遍，碰不到任何一条边界规则。不为了配合自己补的边界去改页面的默认条件、默认数据或主流程的步骤。例如补了"只能审核近 7 天提交的申请"，就把列表默认改成只显示近 7 天，这是在让主流程迁就补的规则，这条边界本身就补错了。
4. 并发和性能不写。并发数、响应时间、吞吐量、数据库和接口层面的限制由研发定，不进 PRD 和原型。
5. 示例数据的量级跟着场景走。原型列表的总条数、金额大小、时间分布和场景一致。超限这类状态靠改条件触发，不靠把默认数据编得离谱。

下面是示例值的对照。需求是"区域经理每周批量审核各门店的退货申请"：

| 写法 | 问题 |
| --- | --- |
| 批量审核单次最多 1,000 条，示例数据有 3,286 条待审核 | 上限是套的常见数字；默认数据编得离谱，和"每周几十条"对不上 |
| 只能审核近 7 天提交的申请，列表默认只显示近 7 天 | 为了配合补的边界改了默认条件 |
| 一个区域每周约几十条申请，批量审核单次最多 200 条，约是平时一周的几倍，只有积压很久才会碰到 | 从场景推出量级，平时碰不到，依据写进确认单 |

### 4. 验收要点

- 3 到 5 条，写成表格，列为前提、操作、预期结果、对应规则。
- 每条至少对应一条业务规则。"对应规则"列写规则编号和规则名称，如"R1 退货期限"。
- 至少有一条覆盖异常或阻断的情况。只验证正常路径，最容易出错的地方就没人验。

### 状态流转（按需）

- 用表格写，列为：当前状态、触发动作、目标状态、操作角色、备注。
- 不画状态机图。

### 异常处理（按需）

- 用表格写，列为：异常场景、处理方案。只写本需求里会发生的。

### 角色和权限（按需）

- 用表格写，列为：角色、可见页面、可用操作、数据范围。

### 术语、风险、数据埋点（按需）

- 用表格写，只写本需求涉及的内容。

## 文件格式

- Markdown，UTF-8 编码。
- 标题层级不超过四级。
- 字段、规则、权限用表格写。

## 默认模板的骨架

用默认模板时，按下面的骨架写。花括号里是要替换的内容。骨架里的业务是门店退货，数值都是示例值。

骨架的用法：

- 规则描述按"规则名称：完整内容"的格式写，如"退货期限：顾客购买满 30 天后，店员不得提交该订单的退货申请。"
- 一个功能有多个页面时，"页面交互"下每个页面各写一组规则块，每组以"页面：页面名称"开头。
- 多个功能时，3.1、3.2 依次排，规则编号全文连续。
- 骨架里的字段规则是表单字段的列。列表字段用另一组列：字段、显示格式、交互与校验、权限与状态。
- 按需章节只在出现条件成立时才写。
