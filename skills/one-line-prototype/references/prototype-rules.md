# 原型规则

本文件在流程第 4 步列页面清单、第 6 步做原型时使用，第 7 步按文末的自查清单检查。它说明原型要达到什么样子、先想什么再动手、怎么用 `assets/prototype-base.html`。怎么把页面设计得成熟，见 prototype-design-reference.md。原型上的文案按 writing-rules.md 第 13 条写。

## 原型是拿来做什么的

评审人看原型，是在判断"做出来是不是这样"。所以原型要像一个真实运行的系统：有系统标志、带图标的导航、面包屑、当前用户，页面有标题和说明，列表里的数据像真的，操作点下去有结果。只把 PRD 的规则表逐条翻译成控件，规则是齐的，页面却很单薄，评审人很难把它当成要上线的系统来看。

本文件只有下面七条是硬约束，其余内容和 prototype-design-reference.md 都是参考：用来告诉你一个成熟的原型通常有哪些东西，按需求自己判断，可以不照做，也可以做得更多。

## 七条硬约束

| 约束 | 原因 |
| --- | --- |
| 一个 HTML 文件，不引用外部的脚本、样式、字体和图片，断网能打开 | 用户常把原型转发给别人，对方不一定能联网 |
| 原型里的业务规则和 PRD 一致。做原型时想到了 PRD 没有的规则，先补进 PRD，再按 confirmation-sheet.md 记入确认单 | 研发照 PRD 实现，评审人照原型确认，两边不一致就有一边是错的 |
| 规则能通过灯泡对回 PRD 的编号，右上角有"规则标注"开关 | 用户要能逐条核对原型和 PRD |
| 主流程能从第一步点到最后一步 | 点不通的地方，评审人无法判断交互对不对 |
| 打开时是主流程的正常状态，默认状态下点主操作，走到的也是正常路径 | 评审人第一眼看到的应该是平时的样子。空数据、超限、被拦截这类状态要能通过操作看到，不作为默认状态。例如示例数据的默认查询结果要落在能正常导出的范围内，超限靠改查询条件触发；否则评审人第一次点主操作就看到报错 |
| 不用浏览器自带的 `alert`、`confirm`、`prompt` | 它们的样子和系统不一致，也挡住了演示 |
| 没有界面参考时，设计令牌和主色沿用基础文件的；基础文件里已有的组件样式不改，页面自己的样式写在"页面样式"一段 | 主题和主色要和 PM Agentic Cookbook 一致，用户以后转去完整流程时衔接得上；基础脚本依赖已有的类名，改了交互会坏 |

## 第 4 步：列页面清单

写 PRD 和做原型之前，先按页面列一份清单，把页面上有什么、各自在什么状态下怎么表现想清楚。清单只给你自己用，不写成文件，不出现在回复、PRD、原型和确认单里，也不拿去问用户。

每个页面写下面八项：

| 项 | 写什么 |
| --- | --- |
| 菜单位置 | 在导航的哪一组、叫什么、排在哪个菜单之后；是已有页面还是本次新增 |
| 功能 | 这个页面能做的事，逐项列出。本次新增或改动的标出来，已有的也列上 |
| 页面区域 | 从上到下有哪些区域，如标题区、提示条、指标、查询区、列表、分页 |
| 按钮和操作 | 每个按钮和行操作：名称、位置、是不是主操作、什么角色和什么数据状态下出现、什么时候禁用以及禁用原因、点击后发生什么 |
| 弹层 | 每个弹窗和抽屉：从哪里打开、里面展示哪些信息、有哪些输入、底栏有哪些按钮、提交后发生什么 |
| 状态 | 默认状态是什么样；还有哪些状态（空数据、搜索无结果、加载中、失败、无权限、超限、被拦截），各自怎么触发、界面怎么表现 |
| 数据状态 | 列表里的记录有哪几种状态，每种状态下行操作有什么不同 |
| 要显示的规则 | PRD 的哪些规则在这个页面上体现，各自以什么形式显示（说明文字、提示条、弹层摘要、禁用原因、说明气泡），灯泡挂在哪个元素上 |

列清单时想三件事：

1. 每个页面定一个主操作。列表页的新建、导出、导入这类列表级操作放在查询栏右端，依次排在"查询""重置"之后，列表标题区只放标题；没有查询栏的页面，主操作放在页面标题区右侧。按钮带图标，本次新增的操作用次要按钮或主要按钮，和"查询"一眼能分开。
2. 每个弹层先想"系统的使用人在这里要看到什么才敢点确认"，把这些信息列出来。例如导出弹窗写明导出范围、预计条数、文件格式和文件名，而不是一句"确定导出吗"。
3. 每条业务规则至少落在一个页面元素上。落不下去的规则，说明页面上缺一个展示它的地方。

PRD 的"页面交互"照这份清单写，原型也照它做。做原型时想到了更好的交互，先改 PRD 的"页面交互"，两边保持一致。

## 原型做到什么程度

- PRD"功能需求"里写到的每个页面和弹层，原型里都有。
- 本次需求改的是已有页面时，把这个页面原有的内容也画出来，如原有的列、筛选和行操作，页面看起来才完整。
- 示例数据贴合业务：名称、金额、时间像真的，不用"测试 1""测试 2"。每个列表至少 3 行，覆盖 PRD 里出现的每个状态。列表的总条数、金额大小、时间分布跟着场景的量级走，指标、统计数字和列表总数互相对得上，超限这类状态靠改条件触发，不靠把默认数据编得离谱。
- 交互做到下表的程度。数据的持久保存、真实的后端请求和登录不做，它们不影响确认交互和规则。

| 要实现的 | 做法 |
| --- | --- |
| 页面切换和弹层开关 | 按 PRD 的页面结构 |
| 主流程上的按钮反馈 | 按 PRD 的按钮规则给提示、跳转或二次确认 |
| 按钮的展示条件和禁用态 | 禁用时悬停能看到原因 |
| 表单的必填和格式校验 | 错误文案按 PRD 的字段规则，显示在字段下方 |
| 页面状态 | 空数据、搜索无结果这类状态能通过操作看到 |
| 状态变化 | 操作后，列表里对应记录的状态按 PRD 的状态流转变化 |
| 角色切换 | PRD 有 2 个及以上角色时，点顶栏右侧的头像切换身份，每个角色看到自己的导航和页面 |

## 规则、交互设计和示意内容

writing-rules.md 第 6 条"不编造"和确认单的完整性要求，管的是业务规则和数值。原型里另有一类内容是示意，处理方式不同：

| 类别 | 例子 | 怎么处理 |
| --- | --- | --- |
| 业务规则和数值 | 导出只含已支付的订单、文件保留 30 天、停用原因必填 | 必须有来源；你补的逐条记入确认单，取值按 prd-template.md 的"补的规则要贴合场景"定 |
| 本次需求的交互设计 | 导出弹窗里展示预计条数和文件名、导出按钮排在查询栏右端 | 写进 PRD 的"页面交互"；影响实现的记入确认单 |
| 示意内容 | 已有页面原有的列和筛选、原有的行操作、头像和用户名、通知、示例数据、系统名 | 自由补，让页面像真实的系统。不逐条记入确认单，在确认单的"说明"里写一句：原型里已有页面的内容和示例数据是示意，不代表现有系统的实际字段 |

拿不准一项内容属于哪一类时，看研发会不会照着它去实现本次需求：会，就按前两类处理；不会，就是示意。示意内容补得太少，列表只剩几列、没有行操作，页面就不像真的。

上表的数值都是示例值。

## 规则怎么呈现

规则先写在界面上，这是系统本身该有的文字，评审人不用悬停也能看到，"规则标注"开关关掉后仍然在：

- 字段下方的说明文字，如"最多 200 字"。
- 页面或弹层里的提示条，如"导出文件保留 30 天，过期后需要重新导出"。
- 弹层里的摘要信息，如导出范围、预计条数、文件名。
- 按钮禁用时悬停显示的原因。
- 操作旁的说明气泡，用于一句话说不完的口径。

然后在对应的元素上写 `data-rule="R3"`，多条用空格分隔。基础脚本在元素旁生成一个小灯泡，悬停或点击展开气泡，列出规则编号、名称和内容。页面上不直接写规则编号，成熟的系统不会把编号贴在界面上。

- 灯泡由基础脚本生成，不手写。一个元素只有一个灯泡，多条规则共用。
- 字段的 `data-rule` 写在 `.field` 上，灯泡出现在字段标签旁。一个字段里有多个输入控件时也写在 `.field` 上。
- 按钮、徽标上的 `data-rule`，灯泡出现在元素后面；表头、提示条、卡片和弹层上的，灯泡出现在文字旁。
- 编号照 PRD 的写法。PRD 跟随历史文档用 `GZ-01` 时，`data-rule` 也写 `GZ-01`。
- 原型里出现的每个规则编号，PRD 里都有定义；`RULES` 里没有的编号，灯泡显示为红色。PRD 里能在界面上体现的每条规则，原型里至少有一个灯泡。

## 样式从哪里来

1. 用户提供了界面参考：照用户的样式做，新组件沿着已有样式延伸。基础文件的页面结构和基础脚本照用，样式区可以改，类名不改。
2. 没有提供：用基础文件的默认样式，在确认单的"说明"里写明。

没有界面参考时，基础文件的样式分三段处理：

| 段 | 做法 | 原因 |
| --- | --- | --- |
| 设计令牌 | 不改。用户要换主色时，只改 `--primary` 一个变量 | 主题和主色要和 PM Agentic Cookbook 一致 |
| 组件样式 | 不改原有的类 | 基础脚本依赖这些类名 |
| 页面样式 | 可以新写。颜色、字号、间距、圆角、阴影用令牌变量，如 `var(--color-gray-500)`、`var(--space-4)`，不写死色值 | 给页面设计留出空间，同时保住主题一致 |

新写样式或做基础文件里没有的组件时，交互照本文件和 prototype-design-reference.md 已有的规则；没写到的照 Ant Design 的组件交互规范，不凭空自创一套。

默认样式用于 B 端 PC 后台。移动端和面向消费者的需求没有专门规范，参照 Ant Design Mobile 的惯例做，在确认单的"说明"里写明。

## 怎么用基础文件

1. 完整读 `assets/prototype-base.html`，复制全部内容作为原型文件的起点。
2. 删掉注释标出的示例部分：示例导航、示例页面、示例弹层、示例页面的样式和脚本。删之前看一遍示例页面，它示范了一个像样的页面通常有什么：副标题、写在界面上的规则、指标、带快捷日期的查询栏、排在查询栏右端的带图标的导出和新建、勾选和已选条数、行操作、带摘要的操作弹窗、任务记录和失败说明。
3. 把 `<title>` 和 `.brand-name` 改成系统名。
4. 在"原型数据"脚本块里填 `RULES` 和 `USERS`。`RULES` 从 PRD 的业务规则表抄录，键是规则编号，值是名称、类型、描述。`USERS` 是系统的使用人，写姓名和角色；PRD 有几个角色就写几个人，第一个是打开时的身份。
5. 导航写在 `.nav` 里：`.nav-group` 是分组名，面包屑会用到；导航项写成 `<a class="nav-item" data-goto="页面标识"><svg class="i"><use href="#i-list"/></svg>菜单名</a>`。有多个角色时，导航项用 `data-roles` 写能看到它的角色，多个用空格分隔。
6. 每个页面写成 `<section class="page" data-page="标识" data-title="页面名">`，放在 `.content` 里，开头是 `.page-head`，里面是 `.page-title` 和 `.page-subtitle`；没有查询栏的页面，主操作写在 `.page-head` 的 `.actions` 里。详情这类不在导航里的页面加 `data-parent="上级页面标识"`，面包屑会带上上级页面。
7. 弹窗写成 `<div class="overlay" data-overlay="标识"><div class="modal">`，抽屉写成 `<div class="overlay side" data-overlay="标识"><div class="drawer">`，里面依次是 `.overlay-head`、`.overlay-body`、`.overlay-foot`。用 `data-open="标识"` 打开，用 `data-close` 关闭。
8. 页面脚本写在文件末尾的页面脚本块里，只写示例数据、渲染、校验和状态变化。
9. 通知列表在顶栏的 `#notice-menu` 里，是示意内容，按系统改写。

基础文件提供的东西：

| 类别 | 内容 |
| --- | --- |
| 图标 | `<svg class="i"><use href="#i-名称"/></svg>`。可用：home、chart、list、file、search、plus、edit、trash、eye、download、upload、export、refresh、settings、bell、user、users、calendar、clock、filter、info、warning、success、error、close、left、right、down、more、copy、help。页面脚本里可以用 `icon('search')` 生成 |
| 布局 | `.page-head`、`.page-title`、`.page-subtitle`、`.actions`、`.card`、`.card-head`、`.card-title`、`.card-body`、`.card.stats` 和 `.stat`、`.tabs` 和 `.tab-panel`、`.section` |
| 列表 | `.toolbar`、`.toolbar-item`、`.search`、`.range`、`.chips`、`.table-wrap`、`.table`（`.num` 数字右对齐，`.col-check` 勾选列；表头最后一列叫"操作"时自动固定在右侧，只有文字、超过 20 个字的单元格自动省略并在悬停时显示全文）、`.mono` 编号、`.ellipsis` 长文本、`.cell-sub` 第二行小字、`.batch-bar` 已选条数、`.empty` 空状态、`.pager`、`.progress` 进度 |
| 表单 | `.form`、`.field`（必填加 `required`）、`.field-label`、`.input`、`.choices` 和 `.choice` 单选多选、`.field-hint`、`.optional` |
| 反馈 | `.alert-info`、`.alert-success`、`.alert-warning`、`.alert-error` 提示条；`.badge-success`、`.badge-warning`、`.badge-error`、`.badge-processing`、`.badge-default` 状态；`.summary` 弹层摘要；`<span class="help" data-tip="说明"></span>` 说明气泡；`data-tip` 悬停提示 |
| 按钮 | `.btn` 加 `btn-primary`、`btn-secondary`、`btn-outline`、`btn-danger`、`btn-text`，小号加 `btn-sm`。不可用的按钮写 `aria-disabled="true"` 和 `data-tip="原因"`，不用 `disabled`，带 `disabled` 的按钮收不到悬停 |
| 函数 | `goto(页面)`、`openOverlay(弹层)`、`closeOverlay(弹层)`、`showSuccess(文字)`、`showError(文字)`、`confirmDialog({ title, content, okText, cancelText, tone })`、`setFieldError(字段, 文字)`、`clearFieldErrors(范围)`、`renderPager(元素, 总数, 页码, 每页条数, 翻页回调)`、`currentRole()`、`currentUser()`、`icon(名称)` |
| 事件 | `pagechange`、`overlayopen`、`rolechange` |

`showSuccess` 和 `showError` 在顶部居中显示，约 3 秒后消失。重要的失败要说明原因时用 `confirmDialog`，`cancelText` 传 `null` 时只有一个按钮。`confirmDialog` 的 `tone`：破坏性操作 `'danger'`，锁定或对外提交 `'warning'`，中性确认 `'info'`。打开弹层时基础脚本会清空里面的表单，编辑时在 `overlayopen` 事件里回填数据。

## 交互建议

用户提供了界面参考时，对照本文件和 prototype-design-reference.md 提交互上的改进建议。

- 只提交互，不提视觉，限于反馈、提示、状态、防误操作四类。例如按钮禁用时没有说明原因、校验错误离字段太远、不可撤销的操作没有二次确认、提交后没有加载状态、列表没有空状态。
- 最多 5 条，只提影响系统的使用人完成任务的。
- 写进确认单的"交互建议"部分，格式见 confirmation-sheet.md。默认不改原型。
- 用户说"采纳第 N 条"后，同步改原型和 PRD 里对应的规则。

## 交付前自查

1. 断网后能打开，页面显示正常。
2. 文件里没有 `http://` 或 `https://` 开头的外部资源引用。
3. 主流程能点通。
4. 打开时是主流程的正常状态；不改任何条件，直接点每个主操作，走到的都是正常路径，不被拦截。
5. 逐页对照页面清单：清单里的菜单、功能、按钮、弹层、状态都做出来了。
6. 每条能写成界面文字的规则，在界面上能直接看到，不用悬停灯泡。
7. 每个灯泡展开的编号在 PRD 里存在，没有红色灯泡；PRD 里能在界面上体现的规则都有灯泡。
8. 页面上不直接显示规则编号；一个元素旁只有一个灯泡。
9. 关掉"规则标注"开关后，页面上看不到任何灯泡。
10. 页面样式里没有写死的色值，用的是令牌变量。
11. 示例导航、示例页面、示例弹层、示例样式和示例脚本已经删掉。
12. 原型上的文案符合 writing-rules.md 第 13 条。
