# 提问

本文件在流程第 3 步使用，时间是分级为简化之后、列页面清单之前。它规定哪些问题值得问、怎么问、用户没回答时怎么处理，并给出示例和反例。

## 什么问题值得问

同时满足下面三条才问：

1. 是不确定的业务规则，或需求里不清晰的地方。
2. 答案不同，PRD 的内容或原型会不同。
3. 从需求描述和历史文档里得不到答案。

不满足的问题，答案不改变产出物，问了只会拖慢用户。

## 怎么问

- 只问一轮。用户要的是尽快拿到能改的东西，多轮来回比直接在原型上改更慢。
- 问完就停，等用户回答，见 SKILL.md 第 3 步。不等回答就按推荐值写下去，用户就没有机会改掉会改变产品的规则。
- 最多 5 个问题。没有满足上面三条的问题时不问，直接写 PRD。
- 一次把所有问题列出来。每个问题给 2 到 4 个选项，并附一句推荐理由。用户只要扫一遍就能答完。
- 推荐的选项必须放在第一个，即 A。用户看每题的 A 就知道推荐的是什么，回"都按推荐"时不用逐题去找。
- 告诉用户可以回"都按推荐"。
- 不向用户索要材料。用户没给的，按默认规则处理。很多用户手上没有现成材料，要了也拿不到。
- 只有一种例外：用户的原话指向一份具体的材料，但没有附上，例如"按我们公司的模板写""跟现有的审批页面一样"。这时可以问一次，作为这一轮问题中的一个，不单独再问一轮。选项 A 是请用户发来，后面给一个不发的选项，如"没有现成的，按默认结构写"。用户没有发来时按默认规则处理，并记入确认单。用户明确说过有这份材料，凭空猜它的内容，写出来的 PRD 会和用户手上的文档对不上。

例外情况的问法示例：

```
1. 你提到按公司的模板写，能把模板发给我吗？
   - A. 我发给你（推荐：PRD 的章节和用语会和你们以往的文档一致）
   - B. 没有现成的，按默认结构写
```

## 历史文档是上一个版本时

用户给的历史文档就是本次需求的上一个版本，即同一个模块、本次在它上面迭代或补充时，加问一题。它和上面的例外一样，算在这一轮的 5 个问题内。单独写一份还是出完整的新版本，决定了新文档有多长、评审人看什么，从文档里判断不出来。

- A 是"单独写一份，只包含本次需求"，作为推荐。
- B 是"在原文档的基础上出一份完整的新版本，另存为新文件，原文件不动"。
- 没问到或没回答时按 A 写，并记入确认单。两种写法的具体做法见 prd-template.md。

问法示例：

```
1. 你给的 V2.3 是供应商台账这个模块的上一版。这次的 PRD 怎么出？
   - A. 单独写一份，只包含停用功能（推荐：评审人只看本次改动，不用在整份文档里找新增的部分）
   - B. 在 V2.3 的基础上出一份完整的新版本，另存为新文件，V2.3 不动
```

## 问题超过 5 个时怎么取舍

按"答案对产出物的影响范围"从大到小排，取前 5 个。改变流程、状态或页面数量的问题，排在只影响一个字段的问题前面。

没问到的问题按你的推荐值处理，记入确认单。确认单的格式见 confirmation-sheet.md。

## 用户没有全部回答时

- 只回答了部分问题：没回答的按推荐值处理，记入确认单。
- 要求直接出结果：全部按推荐值处理，全部记入确认单。

## 提问的格式

运行环境提供了让用户点选回答的提问工具时，用这个工具提问，例如 Claude Code 的 AskUserQuestion、DeepSeek Harness 的 ask_user_question。用户点一下就能答，不用打字。

- 分级结果写在调用工具之前的那句回复里。
- 每个问题是工具里的一项。推荐的选项放第一个，标签末尾加"（推荐）"，推荐理由写在这个选项的说明里。
- 工具一次放不下 5 个问题时，分两次调用，仍算这一轮。
- 工具调用失败，或者没有人能在界面上回答时，改用下面的文字格式。

没有这类工具时，分级告知和提问放在同一条回复里，用文字格式。选项写成每题下面的子列表，每个选项单独一行，在网页里显示时不会挤成一段：

```
这个需求判定为简化：{理由}。

开始写之前有 {N} 个问题。每个问题我标了推荐的选项，你可以直接回"都按推荐"。

1. {问题}？
   - A. {选项}（推荐：{一句理由}）
   - B. {选项}
```

## 示例一：门店退货

需求描述：给门店加一个退货申请功能，店员提交，区域经理审核。

下面的数值都是示例值。

```
这个需求判定为简化：只涉及一个二级菜单、一个带状态的对象（退货申请）和两个角色，没有命中任何复杂条件。

开始写之前有 3 个问题。每个问题我标了推荐的选项，你可以直接回"都按推荐"。

1. 退货有没有期限？
   - A. 购买后 30 天内可以退（推荐：一个月足够顾客发现问题回店，门店也不会收到放了很久的商品）
   - B. 购买后 7 天内可以退
   - C. 没有期限

2. 审核驳回后，店员能不能修改后重新提交？
   - A. 可以，在原申请上修改（推荐：保留驳回原因，便于对照）
   - B. 不可以，只能新建一条申请

3. 区域经理多久没有审核算超时，超时后怎么处理？
   - A. 满 3 天提醒区域经理，不自动关闭（推荐：自动关闭会让店员重新提交）
   - B. 满 7 天自动关闭申请
   - C. 不设超时
```

## 示例二：会议室预订审批

需求描述：给公司的会议室预订加一个审批，员工预订大会议室要行政专员审批通过才算订上。

下面的数值都是示例值。

```
这个需求判定为简化：只改动已有的会议室预订功能，涉及一个带状态的对象（会议室预订）和两个角色，没有命中任何复杂条件。

开始写之前有 4 个问题。每个问题我标了推荐的选项，你可以直接回"都按推荐"。

1. 哪些会议室算大会议室？
   - A. 按容纳人数，20 人及以上的算（推荐：不用另做设置页面）
   - B. 由行政专员在会议室设置里逐间标记

2. 提交预订后、审批通过前，这个时段还能不能被别人预订？
   - A. 不能，提交后就占住时段（推荐：避免两个人的预订同时被通过）
   - B. 能，谁先被审批通过算谁的

3. 行政专员一直没有审批，怎么处理？
   - A. 会议开始前 2 小时仍未审批，系统自动驳回并通知员工（推荐：时段不会一直被占着）
   - B. 一直等，不做处理
   - C. 会议开始前 2 小时仍未审批，系统自动通过

4. 审批通过后，员工能不能取消预订？
   - A. 会议开始前随时可以取消，取消后时段释放（推荐：不需要再走一次审批）
   - B. 会议开始前 1 小时内不能取消
```

## 反例：不该问的问题

以示例一的门店退货需求为例，下面三个问题不该问。

| 不该问的问题 | 为什么不该问 |
| --- | --- |
| 列表每页显示多少条？ | 答案不改变产品形态。按默认值 10 条写，记入确认单 |
| 你们有没有现成的 PRD 模板可以发我？ | 这是索要材料 |
| 退货申请需要哪些字段？ | 范围太大，用户答不了。先按常见字段写出来，让用户在原型上改 |
