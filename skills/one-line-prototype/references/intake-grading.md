# 准入分级

本文件在流程第 2 步使用，时间是读完输入之后、提问之前。它规定怎么判定需求走简化流程还是完整流程，判为复杂时怎么引导用户安装完整流程，以及怎么交接。

## 判定时机

- 每次运行只判定一次，在提问之前。分级决定了后面要不要提问、要不要产出，放到提问之后就白问了。
- 判定条件只写在本文件。其他文件需要时写"见 intake-grading.md"，不复述条件。条件写在多处，改了一处漏了另一处，判定就会前后不一致。

## 档位

| 档位 | 对应的需求范围 | 处理方式 |
| --- | --- | --- |
| 简化 | 子功能详细需求、迭代需求 | 本 skill 直接产出 PRD、流程图和原型 |
| 复杂 | 含多个菜单或多个状态机的功能模块、系统级规划 | 进入下文的安装引导 |

四种需求范围的含义：

| 需求范围 | 含义 |
| --- | --- |
| 子功能详细需求 | 在已有模块里展开一个二级菜单、一个页面或一项能力，写清入口、交互、字段、规则、异常和权限 |
| 迭代需求 | 改造已经在用的功能，写清改造前后的差异和影响范围 |
| 功能模块级 | 新建或重构一个完整的业务模块 |
| 系统级规划 | 从零新建一个系统 |

## 判定条件

命中下面任意一条，判为复杂。一条都不命中，判为简化。

1. 新建一个系统，或新建一个完整的业务模块。
2. 涉及 2 个及以上二级菜单。
3. 有 2 个及以上带状态流转的业务对象。
4. 需要和外部系统对接。
5. 有 3 个及以上角色，并且各自的操作流程不同。
6. 会改变产品形态的歧义超过 5 个，一轮提问问不完。

命中任何一条的需求，都需要领域模型、跨模块的一致性核对或接口约定，简化流程不做这些，硬做会产出一份看起来完整、实际缺依据的 PRD。

## 告诉用户

判定后用一句话告诉用户结果和理由，句式是：

```
这个需求判定为【简化 / 复杂】，理由是【命中的条件，或"没有命中任何复杂条件"】。
```

用户可以改判。改判后按用户的判定继续，不再争论。需求在用户的系统里处于什么位置，用户比你清楚。

## 复杂需求的安装引导

1. 检查完整流程是否已经可用。判断依据是 create-prd 这个 skill 当前能不能调用。
2. 已经可用：告诉用户这个需求建议走完整流程，问是否转入。用户同意转入时，按下文"交接给完整流程"做；不同意时，按第 5 步处理。
3. 不可用：问用户是否安装 PM Agentic Cookbook，同时给出下面三样信息。
   - 链接：`https://github.com/Sunnyshinnny776/pm-agentic-cookbook`
   - 安装方式：运行 `git clone https://github.com/Sunnyshinnny776/pm-agentic-cookbook.git` 获取仓库，再把需要的 skill 目录放进 Agent 的 skill 目录，或安装仓库里各 skill 目录下的 `skills/<skill>/dist/<skill>.skill`。装好后按仓库里的 `process/overview.md` 逐阶段推进。安装会写入用户的环境，动手前必须得到用户同意。
   - 推荐理由：完整流程会先建领域模型，有独立的检查环节，有验收台账，会核对跨模块的一致性。简化流程这四样都没有。
4. 用户选择安装：引导安装。装好后按下文"交接给完整流程"做。
5. 用户选择不安装：按简化流程继续。交付时在确认单的"说明"部分里写明简化流程没有做第 3 步列的四样，确认单的格式见 confirmation-sheet.md。这段说明不得写进 PRD，PRD 是给评审人和研发看的，流程上的缺口只和用户本人有关。只有判为复杂、用户选择不安装时才写这一条；判为简化的需求不写。

## 交接给完整流程

把用户的需求描述，以及用户已经补充的信息，整理成一段需求摘要，交给完整流程作为输入。本 skill 到此结束，不再产出 PRD 和原型。两套流程各出一份 PRD 的话，用户会拿到两份口径不同的文档。
