# 从需求到原型

用户给一句话需求，你问清会改变产品的规则，按需求大小分流，然后产出一份精简 PRD、每个功能一张流程图、一个可交互原型，以及一份只给用户本人看的确认单。用户只看确认单和原型，就能判断哪些地方要改。

## 什么时候用，什么时候不用

- 用于要被做出来的、有界面和规则的功能。用户不限岗位：产品经理、兼做需求的运营和业务人员、创业者、找外包的甲方、独立开发者都可以用。
- 用户提供了方案类文档作为样本时，产物按样本的结构写，不限定为 PRD。
- 不用于营销方案、汇报材料、调研报告这类通用写作。
- 不用于没有界面的需求，例如纯接口、纯数据任务。遇到时告诉用户本 skill 不适用，然后停止。

## 输入

| 输入 | 是否必需 | 说明 |
| --- | --- | --- |
| 需求描述 | 必需 | 一句话或一段话 |
| 历史文档 | 可选 | 用户以前的 PRD、需求说明或方案文档 |
| 界面参考 | 可选 | 页面截图、设计规范、组件说明、现有系统的链接 |
| 输出位置 | 可选 | 用户指定的目录 |

不盲目向用户索要材料，没给的按默认规则处理。唯一的例外见 references/questions.md。

## 产出物

| 产出物 | 文件 |
| --- | --- |
| 精简 PRD | `<需求名>-PRD.md` |
| 流程图，每个功能一张 | `assets/<需求名>-<功能名>-流程图.svg`，PRD 用相对路径引用 |
| 原型 | `<需求名>-原型.html` |
| 确认单 | `<需求名>-确认单-交付前必看.html` |

- 用户指定了输出目录就用指定的；没有指定时，在当前工作目录下以需求名新建一个目录。
- 同名文件已存在时不覆盖，先告诉用户，由用户决定覆盖还是另存。
- 不修改、不覆盖用户给的任何文件，包括历史文档和界面参考，产出一律写成新文件。

## 流程

按顺序做，不跳步。

1. 读输入。从需求描述里找出要做的功能、涉及的角色和页面。有历史文档时读完整份，按 references/prd-template.md 的"用户提供了历史文档时"记下结构和用语。有界面参考时记下布局、主色、按钮和表格的样式、提示的出现方式。需求没有界面时说明不适用并停止。做完的标志：能说出要做哪几个功能、几个角色、几个页面。
2. 准入分级。读 references/intake-grading.md，判定一次，用一句话告诉用户结果和理由。判为复杂时按该文件做安装引导或交接。做完的标志：用户知道判定结果，复杂需求已经选好转入完整流程还是继续。
3. 提问。读 references/questions.md，问一轮，没有值得问的问题时跳过。有值得问的问题时，运行环境有让用户点选回答的提问工具就用工具问，没有就用文字，格式见 questions.md 的"提问的格式"。第 2 步的分级结果和问题一起发出，发完就等用户回答；用户回答之前不列页面清单、不写 PRD、不做原型。只有用户说了"直接出"才不问。做完的标志：用户回答了，或者说了"都按推荐"或"直接出"。
4. 列页面清单。读 references/prototype-rules.md 和 references/prototype-design-reference.md，按页面列出菜单位置、功能、页面区域、按钮和操作、弹层、状态、数据状态、要显示的规则。清单只给你自己用，不写成文件，不出现在回复和任何产出物里。做完的标志：每个页面有主操作，每个弹层想好了要展示的信息，每条规则落在了页面元素上。
5. 写 PRD 和流程图。读 references/prd-template.md 定结构和内容，"页面交互"照页面清单写；读 references/writing-rules.md 写句子；读 references/flow-diagram.md 给每个功能画流程图。做完的标志：PRD 文件和每张流程图都写进了输出目录。
6. 做原型。PRD 写完后再做，照页面清单做，规则编号以 PRD 为准。按 prototype-rules.md，从 assets/prototype-base.html 开始。做的过程中想到了更好的交互，先改 PRD 的"页面交互"。做完的标志：原型文件写进了输出目录，主流程能点通。
7. 交付前自查。按 writing-rules.md、flow-diagram.md、prototype-rules.md 文末的自查清单逐条检查，原型逐页对照页面清单，再按 references/confirmation-sheet.md 的完整性要求核对 PRD 里每个数值和规则的来源。发现问题直接改。自查的过程和结果不写进任何产出物。
8. 交付。读 references/confirmation-sheet.md，从 assets/confirmation-base.html 写确认单文件，再按该文件的格式回复用户。
9. 修改。用户用一句话说要改什么，你同步改 PRD 和原型，两者保持一致。修改记录和版本号按 writing-rules.md 沿用规则第 11 条。规则编号不重排：删掉的编号不再使用，新增的规则接在最大编号之后，原型的 `RULES` 和 `data-rule` 跟着改。再按 confirmation-sheet.md 更新确认单，在回复里写明改了哪些位置。

## 三条不能破的规则

1. 确认单是单独的文件，只给用户本人看。它的内容不写进 PRD 和原型。
2. PRD 里每个具体数值和每条规则，要么来自用户，要么列在确认单里。
3. 不写"已满足评审要求"这类结论，是否通过由用户决定。

## 停止条件

- 需求没有界面时，说明不适用，停止。
- 用户选择转入完整流程时，按 intake-grading.md 交接后停止，不再产出 PRD 和原型。
- 同一个问题用户两次没有给出可用的答案时，按推荐值继续，并记入确认单。
